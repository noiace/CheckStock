# CheckStock

Веб-прототип складского учёта для одного магазина на маркетплейсах. Показывает каждый товар на каждом складе фулфилмента (ФФ): физический остаток, резерв FBS и доступное количество. Отдельно показывает товары в пути между ФФ, на маркетплейс по FBO и покупателю по FBS.

Поддерживает товары, создание и переименование складов, архивирование без потери остатков, приход, резервирование, отмену и отправку FBS, подтверждение доставки, отправку и приёмку FBO, перемещения между ФФ и историю операций.

## Запуск

Нужны Git, Docker Engine с Compose или Docker Desktop в режиме Linux containers. Локально устанавливать Python, uv и PostgreSQL не требуется. Команды выполняются из корня клонированного репозитория.

1. Скопируйте пример конфигурации:

   ```bash
   cp .env.example .env
   ```

   В PowerShell: `Copy-Item .env.example .env`.

2. В `.env` задайте свой `POSTGRES_PASSWORD` и тот же пароль в `DATABASE_URL`. Для локальной демонстрации пример уже согласован. Если пароль содержит специальные символы, в URL их нужно percent-encode. Хост внутри Docker — `postgres`, порт — `5432`. `.env` исключён из Git и Docker-образа.

3. Запустите приложение:

   ```bash
   docker compose up --build -d
   docker compose logs backend
   ```

   PostgreSQL должен пройти healthcheck; затем backend автоматически применяет Alembic-миграции, загружает демо-данные в пустую базу и запускает Uvicorn. При ошибке подготовки backend не запускается, причина остаётся в логах.

4. Откройте [интерфейс](http://localhost:8000/ui/) или [Swagger](http://localhost:8000/docs). Корневой адрес перенаправляет на интерфейс.

Порты `8000:8000` и `5432:5432` сохранены. Если они заняты, остановите конфликтующий сервис. Для подключения к PostgreSQL с компьютера используйте `localhost:5432` и параметры из `.env`.

Отдельные команды, если нужно повторить подготовку или проверить схему:

```bash
docker compose exec backend uv run --locked alembic upgrade head
docker compose exec backend uv run --locked alembic current
docker compose exec backend uv run --locked alembic check
docker compose exec backend uv run --locked python app/seed.py
```

Остановка с сохранением данных: `docker compose down`. Остатки хранятся в именованном volume `postgres_data`. Не используйте `down -v`, если данные нужны. Изменение пароля в `.env` не меняет пароль уже созданного пользователя PostgreSQL в существующем volume.

## Демо-данные

| SKU | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Seed выполняет заполнение одной транзакцией и только если в базе ещё нет товаров и складов. Существующую базу он не дополняет и не сбрасывает. После расходования товаров, переименования или архивирования склада повторный запуск ничего не восстановит. Параллельные запуски seed сериализованы advisory lock PostgreSQL. Нулевые остатки интерфейс показывает даже без строки `Stock`.

## Стек и структура

Python 3.14, FastAPI, Pydantic 2, асинхронная SQLAlchemy и asyncpg, PostgreSQL 18.1, Alembic, Docker Compose, uv. Интерфейс — HTML/CSS/JavaScript без клиентского фреймворка. Точные версии Python-пакетов зафиксированы в `uv.lock`; сборка использует `uv sync --locked`.

```text
app/models/       таблицы и ограничения PostgreSQL
app/schemas/      входные данные и ответы API
app/services/     складские операции и запись истории
app/routers/      HTTP-маршруты и границы транзакций
app/db/           асинхронные сессии
app/seed.py       первоначальные демонстрационные данные
web/              интерфейс, доступный через FastAPI /ui/
migrations/       последовательность миграций Alembic
tests/            API- и интеграционные тесты на PostgreSQL
compose.test.yml  изолированное тестовое окружение
```

Модели:

- `Product` — товар с уникальным SKU.
- `Warehouse` — склад с признаком `is_active`.
- `Stock` — физическое количество и резерв для пары товар/склад.
- `FBSReservation` — резерв и его переходы до отмены или доставки.
- `FBOShipment` — отправка на маркетплейс до подтверждения приёмки.
- `Transfer` — перемещение между двумя ФФ до приёмки.
- `StockMovement` — событие истории с количеством, складами и ссылкой на операцию.

Приложение запускается существующим способом `uvicorn main:app --app-dir app`: импорты сервисов и роутеров считаются относительно `app/`. Alembic запускается из корня и импортирует модели как `app.models`. Это отдельные процессы; смешивать оба способа импорта моделей внутри одного процесса не следует.

## Правила учёта

`Доступно = физически − резерв FBS`. Резерв остаётся физически на ФФ, но недоступен для других резервов, FBO и перемещений. Проверяется остаток выбранного склада; достаточное количество на другом ФФ не позволяет списать отсутствующий товар.

FBS: `RESERVED → SHIPPED → DELIVERED` или `RESERVED → CANCELLED`. Отмена освобождает резерв. Отправка уменьшает физический остаток и резерв, после чего товар появляется в пути к покупателю. Доставка убирает его из списка находящихся в пути.

FBO: при отправке физический остаток исходного ФФ уменьшается сразу, товар становится `IN_TRANSIT`. Приёмка меняет статус на `RECEIVED`, без повторного списания и без возврата товара на ФФ.

Перемещение: при отправке уменьшается исходный остаток, до приёмки количество числится в пути. Только приёмка увеличивает остаток назначения. Перемещение на тот же склад запрещено.

Склад удаляется логически: `is_active=False`. Его остатки и история остаются видимыми. Новые приходы, резервы, FBO и перемещения с архивным складом запрещены. Уже созданные операции можно завершить, включая приёмку перемещения на архивный ФФ: это сохраняет учёт физически прибывшего товара. Архивирование само не перемещает остатки.

Каждый изменяющий маршрут использует одну транзакцию для остатков, статуса и истории. `flush()` внутри сервиса не завершает транзакцию. При исключении все изменения откатываются.

PostgreSQL `SELECT FOR UPDATE` блокирует изменяемые остатки и операции до конца транзакции. Создание операций также блокирует склады для согласованности с архивированием; при перемещении склады блокируются по возрастанию ID. Это простая, достаточно грубая блокировка для небольшого прототипа. Приход и приёмка перемещения используют `INSERT ... ON CONFLICT DO UPDATE`: параллельное создание ранее отсутствующего остатка не создаёт дубликаты и не теряет количество.

Повторные отмена, отправка и подтверждения возвращают уже достигнутый статус без изменения количества и без повторной записи истории. Недопустимые переходы, например отмена уже отправленного резерва, возвращают конфликт. Повторная **создающая** операция (новый POST прихода или отправки) считается новой операцией; ключей идемпотентности для неё нет.

Ошибки API: `404` — объект отсутствует, `422` — неверные данные, `409` — нехватка, архивный склад или конфликт статуса. Полный контракт доступен в Swagger. История поддерживает фильтры и пагинацию; список находящихся в пути — `/movements/in-transit`.

## Автоматические проверки

```bash
docker compose -p checkstock-test -f compose.test.yml up --build --abort-on-container-exit --exit-code-from tests
docker compose -p checkstock-test -f compose.test.yml down
```

Это отдельный Compose-проект и отдельный PostgreSQL `postgres-test` с базой и пользователем `checkstock_test`. У него нет опубликованного порта и volume основной базы; данные временные (`tmpfs`). Перед тестами применяются реальные миграции и выполняется `alembic check`. Каждый тест очищает только тестовые таблицы, поэтому не зависит от порядка запуска. Fixture до подключения проверяет одновременно драйвер, хост, имя базы и пользователя и отказывается работать с основной базой. Не меняйте эти координаты для запуска тестов на рабочем PostgreSQL.

Pytest проверяет HTTP-ответы и фактические остатки, статусы и историю в PostgreSQL: приходы, нулевые строки, нехватку на выбранном ФФ, резервы, отмену, доставку, FBO, перемещения, архивирование, повторные подтверждения, ошибки входных данных, seed, статические файлы и регистрацию API товаров.

Конкурентные тесты используют независимые соединения. Они удерживают блокировку и ждут, пока оба запроса действительно окажутся в ожидании PostgreSQL, затем освобождают её. Проверяются последние доступные единицы, конкурирующие отправки, отмена против отправки FBS, повторные подтверждения FBS/FBO/перемещения и первый приход на новую пару товар/склад.

Для проверки атомарности тесты намеренно вызывают сбой записи истории и сверяют откат остатков, статуса и количества операций. HTTP-тесты используют HTTPX ASGITransport с реальной PostgreSQL; сетевой запуск Uvicorn и интерфейс проверяются отдельно.

Дополнительный браузерный сценарий находится в `tests/ui_smoke.py`. Ему нужен Playwright с Chromium в отдельном контейнере и свежий тестовый API с демо-данными на `127.0.0.1:18000`; на рабочем экземпляре его запускать нельзя, поскольку он выполняет складские операции. В стандартный pytest-прогон он не входит. Результат проверки интерфейса и особенности сети на машине аудита описаны в `AUDIT.md`.

## Решения, ИИ и ограничения

Существующие слои моделей, DTO, сервисов и роутеров сохранены. ИИ помогал при проектировании и написании части кода; на завершающем этапе использован для аудита, подключения интерфейса и товаров, seed, интеграционных тестов и документации. Сгенерированный код проверяется складскими сценариями на настоящей PostgreSQL, проверкой миграций, конкурентных запросов и отката транзакций. Результаты конкретного запуска приведены в `AUDIT.md`; сценарий объяснения — в `DEMO.md`.

Прототип не содержит авторизации, интеграций Ozon/Wildberries, заказов и адресов покупателей, нескольких магазинов, возвратов и остатков внутри маркетплейса после FBO-приёмки. Он предназначен для локальной демонстрации. Публично развёртывать его без контроля доступа нельзя. Время хранится с часовым поясом и показывается в локальном времени браузера. Названия складов в истории отображаются текущие; отдельного журнала переименований нет. Активные названия проверяются сервисом под транзакционной advisory lock; прямые записи в базу в обход сервиса такой проверки не имеют. Для небольшой демонстрации списки товаров и остатков не имеют пагинации. Резерв FBS можно завершить по ID из результата операции или истории.
